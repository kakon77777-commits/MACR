# MACR v0.5.0a4 Direct Chat UI v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver an on-demand, loopback-only Direct Chat UI that lets the local operator hold full multi-turn conversations with Grok 4.6 or the pinned local Qwythos model, then launch it from a Windows desktop shortcut.

**Architecture:** Add a Direct-specific contract and runtime beside the delegated `TaskContract` runtime. The Direct runtime reuses provider configuration, credential custody, HTTP transport, authority, lease, candidate-vault, event, and accounting primitives, but it builds provider-native message arrays and never invokes `MacrRuntime.invoke()` or worker prompt compilation. A standard-library loopback HTTP server exposes a bounded authenticated API and serves packaged vanilla HTML/CSS/JavaScript; all persistent state remains under the configured D-drive runtime root.

**Tech Stack:** Python 3.11 standard library (`dataclasses`, `sqlite3`, `http.server`, `secrets`, `threading`, `webbrowser`), existing MACR provider transports and SQLite stores, vanilla HTML/CSS/JavaScript, Windows PowerShell 5.1 shortcut launcher.

**Spec:** `docs/superpowers/specs/2026-08-27-macr-v0.5-direct-chat-design.md`

## Global Constraints

- Before each direct `python -m unittest` command, set `PYTHONPATH=src` in that PowerShell process; `scripts/verify.ps1` already supplies the source path itself.
- Product version is `0.5.0a4`; the Direct browser surface and API schema are `0.1`.
- This completes the v0.5 Direct Chat alpha path and does not rename, replace, or implement the separately designed v0.6 architecture.
- Implementation occurs only on `feature/macr-v0.5-direct-chat-ui`, based on exact commit `42ea69479b4cc02c41fda9f0f6746c764cf9d2fa` / tree `605084f538c36435e3e23a04f91c2cefd8ef8260`.
- Do not modify the frozen MSSP live-route worktree, its runtime authority, or its legacy-ledger seal.
- Do not use subagents. Execute inline in the primary session.
- Only `grok` (`grok-4.6`) and `ollama_qwythos` are Direct providers.
- Direct requests use complete multi-turn history, no hidden prompt, no worker instruction, no automatic summarization, no automatic retry, and non-streaming responses.
- The visible system prompt is blank by default; when present, its exact text is the only system message.
- Provider and model are immutable after conversation creation.
- Grok conversations are `archive_only`; Qwythos conversations are `eval_only`; both are `training_eligible=false`.
- The canonical Qwythos model tag is never changed or overwritten by Direct Chat.
- Browser responses, operational events, accounting records, logs, and shortcut arguments never contain credentials, prompts, answers, or local content paths.
- The service binds only to `127.0.0.1` on an OS-assigned port, rejects non-loopback Host/Origin values, serves no CORS headers, and accepts bounded bodies on exact routes only.
- Persistent source/state remains on D:. The Desktop `.lnk` may live in the Windows Desktop shell folder but contains only a D-drive launcher target and no secret.
- `operator_managed` keeps paid-call confirmation disabled and budget behavior warn-only; credential, route, authority, lease, and privacy gates remain fail-closed.
- The launcher must load the xAI key server-side from the existing D-drive credential helper without printing it, start without a visible console, and open the browser on demand.
- No live paid Grok request is made during implementation verification. The operator performs the bounded Grok and Qwythos acceptance conversations from the UI.
