# MACR v0.5 Shared-Core Corrections and Direct Chat v0.1 Design

Date: 2026-08-27

Status: design approved in chat; implementation not yet authorized

Base implementation: `main@be7d61572ba05446c49e47e94aca4ef714e7d284`

## 1. Purpose

MACR v0.5 adds a local Direct Chat product for provider-native conversations
while correcting shared-core weaknesses found during the first multi-process GLM
pilot. It preserves two distinct interaction planes over one provider and
accounting core:

1. **Direct plane** — the operator talks directly to Grok 4.6 or the local
   Qwythos model without Codex, Claude Code, MACR worker instructions, or hidden
   prompt rewriting in the model path.
2. **Coordination plane** — Codex and Claude Code eventually call bounded MACR
   tools through separate host adapters over the same shared core.

The planes do not exchange conversation content in v0.5. Cross-plane context
handoff is a separate future Context Capsule project.

The following were independently confirmed against the base source:

- GLM rejects a non-`stop` finish before parsing usage and cost.
- the JSONL ledger lock is process-local;
- dispatch events lack durable dispatcher/run attribution;
- there is no deterministic contradiction preflight;
- there is no uniform immutable raw-answer store;
- there is no cross-process dispatch lease;
- delegated worker instructions are derived from an English goal-prefix
  heuristic rather than the structured return contract;
- provider completion does not validate the returned answer against the
  declared return contract.

## 3. Scope decomposition

### 3.1 Phase 1 — Direct Chat v0.1 and shared-core corrections

This specification covers:

- shared observation, candidate, accounting, dispatch, and preflight repairs;
- local Direct Chat for Grok 4.6 and Qwythos;
- a loopback-only, non-streaming local web UI;
- complete local conversation persistence;
- configurable operator policies with a guarded public default;
- migration from v0.4 without deleting legacy evidence.

### 3.2 Phase 2 — host coordination adapters

A later specification will connect Codex and Claude Code to the unified MACR
core. Both hosts will initially receive the same provider availability, budget
policy, and approval authority. Their host-observed origins remain distinct for
audit. The existing EveMissLab Bridge remains a separate semantic transport and
is consumed through an adapter rather than merged into MACR storage.

### 3.3 Phase 3 — Context Capsule

Cross-plane handoff is deferred. Message selection, whole-thread transfer, and
automatic summaries all lose important properties. A future Context Capsule
must address dependency expansion, context budgets, reversible aliasing,
sensitive-term handling, original-text references, provenance, and preview.

## 4. Goals

- Provide direct, full multi-turn conversations with Grok 4.6 and Qwythos.
- Keep direct prompt content outside OpenAI and Anthropic model contexts.
- Add no generic keyword censorship or hidden system instructions.
- Keep provider credentials out of browser memory and responses.
- Preserve exact provider/model/settings provenance for every conversation.
- Make every dispatched paid call accountably known, estimated, or explicitly
  unknown after dispatch.
- Prevent two independent local processes from accidentally claiming one
  sequential dispatch slot.
- Preserve provider observations before candidate validation.
- Preserve candidate bytes privately without publishing prompt or answer bodies
  in operational or accounting ledgers.
- Keep source and persistent state portable and migration-safe.
- Prepare source-safe configuration for a possible future open-source release
  without authorizing publication.

## 5. Non-goals

- GLM Direct Chat.
- Google Direct Chat.
- Direct-to-Codex or Direct-to-Claude content transfer.
- automatic routing, fan-out, verification, materialization, or acceptance;
- a live three-worker batch;
- automatic retries;
- automatic training or fine-tuning;
- encryption at rest in v0.1;
- changing the canonical Qwythos base weights;
- making an external provider the native Codex engine;
- publishing, releasing, or deploying an open-source distribution.

## 6. Architecture

```text
Loopback browser
      |
      v
Direct Web Server
      |
      v
Direct Session Runtime
   |              |
   v              v
Grok Direct    Qwythos Direct
Adapter        Adapter
   \              /
    v            v
Shared Provider Infrastructure
configuration / credential custody / transport / observation parsing
      |
      +--> Candidate Vault
      +--> Direct Conversation Store
      +--> Accounting and Operational Ledger
      +--> Settings Store
```

The Direct Session Runtime does not accept a `TaskContract` and does not call
`MacrRuntime.invoke()`. Direct and delegated work use different public contracts
and cannot be switched with a generic `mode` flag.

Shared code is restricted to provider configuration, credential custody,
transport, health, response observation, pricing, and normalized error types.
Worker-specific prompt construction and authority checks do not leak into the
direct plane.

## 7. Shared-core corrections

### 7.1 Dispatch identity and cross-process admission

Every run receives a UUID `run_id` before admission. Dispatch and terminal
events carry:

- `run_id`
- `dispatch_id`
- `provider_id`
- `origin_host`
- `origin_identifier_kind`
- `origin_native_id`
- optional `batch_id`
- exact `member_digest` when a batch exists
- `relay_is_authorship=false` for relayed work

Runtime identity is recorded only from a host-observed binding. Familiar labels,
task names, process timing, provider model, and self-emitted names are not
authorship evidence.

A SQLite-backed `DispatcherLease` is the authority for sequential slots. A
contender that loses admission receives a typed `refused_before_network` result.
Ledger observation, process census, and peer completion messages are not leases.

The lease stores holder run, provider, acquired/expiry timestamps, and a
monotonic fencing token. Release must compare both run and fencing token.
Expired leases are recoverable but never silently transferred while the holder
still has a settled active run.

### 7.2 Raw provider observation before validation

Provider transport returns a `RawProviderObservation` before candidate
validation. It contains only fields safely parsed from the response:

- returned model;
- sanitized finish reason;
- usage counts;
- provider-reported or estimated currency cost;
- duration;
- response identity when well-shaped;
- presence and byte length of answer content;
- answer SHA-256 after private capture.

Malformed individual fields remain unknown rather than invalidating other safe
fields. The observation is written before enforcing `finish_reason == stop`,
model equality, output shape, tool absence, answer non-blankness, or candidate
acceptance.

A non-stop, malformed, or otherwise contract-rejected response remains a
terminal candidate failure. Exceeding a soft budget creates an accounting
warning and never changes candidate state. An optional guarded-profile hard cap
is enforced before network use. Observation preservation never turns a rejected
response into a candidate success and never authorizes a retry.

### 7.3 Candidate Vault

Raw answer bytes are stored create-once in a private D-drive Candidate Vault.
The public operational and accounting ledgers contain only observation ID,
byte count, SHA-256, provider/task/run linkage, and candidate state.

Provider, capture, contract, materialization, verification, and acceptance are
orthogonal state fields:

```text
provider_state=completed | incomplete | malformed
capture_state=captured | absent
return_contract_state=valid | invalid | not_evaluated
materialization_state=none | verbatim | transformed
verification_state=pending | passed | failed
acceptance_state=pending | accepted | rejected
```

No later state is implied by an earlier state. Provider completion is not
return-contract validity. Re-materializing an unedited candidate must be
byte-identical. Any extraction, annotation, import rewrite, or semantic edit
creates a new artifact, records extractor/transformer version and builder
provenance, and cannot retain verbatim-materialization status.

### 7.4 Deterministic return-contract compiler and validator

The structured `ReturnContract` and an explicit output grammar compile the
worker system instruction. Goal-prefix heuristics do not control output form.
Changing only the return contract deterministically changes the compiled
instruction and approval digest.

The response passes a separate return-contract validator after raw observation
and answer capture but before materialization. The validator can enforce exact
text, plain source without Markdown fences or prose, structured JSON schema,
and declared summary/evidence presence or absence. A provider may complete
successfully while the returned answer is `return_contract_invalid`.

The raw bytes remain immutable even when invalid. Any allowed extraction is a
transformation with its own digest and provenance; it is never reported as the
provider's verbatim answer.

### 7.5 Deterministic contradiction preflight

Delegated tasks gain a deterministic preflight before approval and network use.
It checks structured import, scope, output, return, and policy clauses plus a
small registry of exact conflict rules. It rejects known contradictions such as
simultaneously forbidding every import while requiring a named import.

It does not claim general natural-language satisfiability. Unknown or ambiguous
prose remains an operator/reviewer concern.

### 7.6 Process census helper

Process census is diagnostic only. The shared helper:

- excludes its own PID;
- requires an exact invoker pattern;
- reports the predicate used;
- passes a self-only zero control;
- counts one launched real invoker as exactly one.

It cannot grant dispatch authority or prove concurrency safety.

## 8. Direct conversation model

### 8.1 Conversation

Each conversation stores:

- UUID conversation ID;
- exact provider and model;
- created and last-active timestamps;
- visible system-prompt profile ID, version, and exact content hash;
- provider settings snapshot and hash;
- settings profile name and version;
- `encryption=none`;
- dataset role and training eligibility;
- archive state;
- last context estimate and warning state.

Provider and model are immutable after creation. Cross-provider comparison
requires a separately created conversation; v0.1 does not copy context between
them.

### 8.2 Messages

Messages store conversation ID, stable ordinal, role, exact content, creation
time, run ID, provider observation linkage, and local display state. A completed
assistant response is inserted atomically only after the full response arrives
and its observation is durable.

Partial tokens are never stored as conversation messages.

### 8.3 Provider-specific dataset policy

Grok conversations use:

```text
dataset_role=archive_only
training_eligible=false
provider_improvement_preference=allowed
```

The preference is recorded but does not claim that a provider retained,
trained on, or deleted data. The adapter maps it only to documented provider
controls; otherwise the effective provider training state is `not_asserted`.

Qwythos conversations use:

```text
dataset_role=eval_only
training_eligible=false
```

The exact Ollama tag and available model digest are pinned at conversation
creation. The canonical Qwythos base is immutable. Future experiments create
named derived variants with separate datasets, adapters, provenance, and
evaluation records; they never overwrite the canonical base.

## 9. Multi-turn context

Direct Chat preserves complete conversation history and does not silently
summarize, compact, or drop early messages. The request builder sends the full
history that fits the exact provider context contract.

The UI warns as the estimated context approaches the model limit. If the next
request would exceed a known hard provider limit, it receives a typed local
refusal before network use. The operator may archive and start a new
conversation. Automated compaction and Context Capsule handoff are out of
scope.

## 10. Non-streaming response projection

The request lifecycle is:

```text
created -> admitted -> dispatched -> observed -> completed
                              |         |-> rejected
                              |-> cancelled_or_unsettled
created/admitted -> refused_before_network
```

The UI does not render tokens incrementally. While a request is active it shows
provider, model, start time, elapsed time, and a truthful generating state. It
does not fabricate a progress percentage.

After full observation and validation, the immutable completed response is
passed to a `ProjectionRenderer`. The v0.1 renderer emits local HTML/Markdown.
Future projection-display research can replace the renderer without changing
provider, session, or accounting contracts.

Cancellation stops the UI wait and attempts to close the client transport. If
provider-side cancellation or billing cannot be proven, the run remains
`unsettled` or `unknown_after_dispatch`. A late result is preserved privately
but does not silently enter the conversation; the operator may explicitly
recover it.

## 11. Local web service

The service uses a minimal Python standard-library HTTP server and vanilla
HTML/CSS/JavaScript. It has no frontend build chain and loads no CDN, remote
font, analytics, advertising, or third-party assets.

Security properties:

- bind only to `127.0.0.1` on an OS-assigned port;
- reject non-loopback Host and Origin values;
- use exact routes and bounded request bodies;
- expose no CORS allowance;
- use a random one-time bootstrap token in a URL fragment, exchange it for an
  HttpOnly SameSite session cookie, then invalidate it;
- never serialize provider credentials into browser responses or logs;
- use one running instance guarded by a local instance lease.

An on-demand launcher starts the service without a visible console and opens
the browser. The default idle shutdown is 30 minutes and is configurable.
Active requests and unsettled accounting prevent idle shutdown. Codex and
Claude Code may start or open the service but cannot read Direct conversations.

## 12. UI surface

The v0.1 UI provides:

- provider cards for Grok 4.6 and Qwythos health;
- provider-pinned conversation creation;
- history, local search, archive, and restore;
- complete non-streaming message projection;
- an input composer;
- a visible system-prompt panel, blank by default;
- a versioned prompt-profile selector;
- an advanced settings panel for provider-supported parameters;
- elapsed generation state and cancellation;
- accounting and soft-budget warnings;
- a settings page.

It does not expose GLM chat, Google chat, host coordination, cross-provider
conversation merging, or cross-plane handoff.

## 13. Settings and presets

Settings are versioned. Every run records profile name, profile version, and
`policy_snapshot_sha256`. Changes apply to new runs and do not rewrite history.

Public distributions default to `guarded`. The local operator deployment uses
an uncommitted `operator_managed` override:

```text
paid_call_confirmation=never
budget_behavior=warn_only
multi_turn=full
automatic_retry=false
accounting=required
```

`custom` permits explicit per-setting choices. Configurable fields include:

- provider enabled state and model;
- cloud-call confirmation behavior;
- soft warnings and optional hard cost policy;
- timeout, maximum output, and context warning thresholds;
- bounded live-conformance permission;
- conversation retention and archive behavior;
- provider-improvement preference;
- idle shutdown;
- future Codex/Claude host-adapter policy;
- future accounting adapter configuration.

Structural invariants are not settings:

- credentials never enter browser state;
- provider/model cannot silently switch;
- dispatcher and authorship cannot be fabricated;
- candidate generation never implies verification or acceptance;
- ledger and provenance records are append-only;
- the canonical Qwythos base is not modified in place;
- GLM receives no undeclared file or patch authority.

## 14. Accounting architecture

### 14.1 Shared operational accounting

All interaction planes write one SQLite accounting database with transactional,
cross-process access. It presents one management view while preserving
non-fungible provider subaccounts for cash, promotional credit, subscription,
and local zero-API-cost usage.

Each invocation records:

- origin host and interaction plane;
- run, task, or conversation identity;
- provider and model;
- requested, dispatched, and terminal timestamps;
- input, output, reasoning, cached, media, or other billable units;
- preflight estimate;
- provider-reported or locally estimated cost;
- currency, price basis, observation date, and funding bucket;
- billing state: `provider_reported`, `estimated`, `zero_local`, or
  `unknown_after_dispatch`;
- non-blocking budget-warning state;
- sanitized failure stage and observation linkage.

Budget warnings do not block calls under `operator_managed`. Provider balance,
quota, rate, or technical failures remain real external failures. Privacy,
credential, approval, routing, and authority failures remain hard local gates.

### 14.2 Future accounting-AI interface

MACR is an AI-expense subledger, not the future authoritative general ledger.
It reserves:

- a versioned append-only `accounting_outbox` for invocation expense events;
- inbound `billing_reconciliation` events for authoritative invoice amount,
  tax, exchange rate, credit, refund, and payment status;
- idempotency keys and payload hashes;
- attachment references and hashes without copying bill bodies into MACR.

The future accounting-AI system owns authoritative reconciliation. Its exact
schema and local management-zone paths are not fixed by v0.5.

## 15. Persistent storage

The local deployment continues to store state under the configured D-drive
runtime root. New logical stores are:

```text
direct/conversations.sqlite3
accounting/accounting.sqlite3
candidates/<provider>/<run-id>/answer.bin
settings/settings.sqlite3
runtime/dispatch.sqlite3
```

The v0.1 Direct database is plaintext and records `encryption=none`. Schema
versioning reserves a later copy-based encryption migration. No encryption key
or password workflow exists in v0.1.

Storage roots become configurable absolute paths for future portability. The
local policy still allows persistent writes only on D. A future public first-run
flow requires an explicit data directory and rejects filesystem roots, home
roots, and other dangerously broad locations.

## 16. Migration

- Preserve the legacy JSONL ledger unchanged.
- Import legacy events copy-only with deterministic imported event IDs and
  source-file hashes.
- Make import idempotent; a second invocation changes zero rows.
- Preserve existing GLM approval records.
- Back up each SQLite database before schema migration.
- Support migration dry-run and readback verification.
- On migration failure, refuse service startup and never create an empty
  replacement database.
- Keep current CLI and `TaskContract` behavior compatible unless an exact
  documented v0.5 migration changes one field.

## 17. Error handling

- Missing key, provider, or local model returns an actionable typed error.
- Lease loss is a no-network refusal.
- Timeout and disconnect do not retry automatically.
- Non-stop and malformed responses preserve safe observation fields before
  candidate rejection.
- Failed or canceled post-dispatch runs never default their cost to zero.
- Browser errors do not reflect credentials, authorization headers, full remote
  error bodies, or sensitive local paths.
- Database, settings, and migration failures are fail-closed.
- Every admitted run reaches exactly one terminal state or remains explicitly
  unsettled.

## 18. Acceptance tests

### 18.1 Offline and synthetic gates

- Direct requests contain no hidden system prompt.
- Provider/model cannot change after conversation creation.
- Grok is `archive_only`; Qwythos is `eval_only`; neither is training eligible.
- Browser APIs never expose provider credentials.
- Non-loopback Host and Origin are rejected.
- Two independent processes contend for one slot: exactly one dispatches and
  the loser receives a typed no-network refusal.
- Dispatch and terminal events join one-to-one by run identity.
- A synthetic non-stop response fails candidate validation while preserving
  exact safe finish, model, usage, cost, and duration fields.
- The answer body is absent from public ledgers and present create-once in the
  private vault with exact bytes and SHA-256.
- A source-only task with `summary=false` and `evidence=false` compiles a
  source-only worker instruction without an evidence/warning request.
- A fenced or prose-wrapped synthetic response is preserved privately but
  becomes `return_contract_invalid` before materialization.
- A plain-source control becomes `return_contract_valid`.
- Changing only the return contract changes the compiled instruction and exact
  approval digest without relying on goal wording.
- Re-materializing the same answer twice is byte-identical.
- A semantic edit changes builder provenance and loses verbatim status.
- Known contradictory tasks fail before approval and network; corrected controls
  pass.
- Census self-only control reports zero and a real invoker reports one.
- Crash recovery leaves no admitted run silently missing or multiply terminal.
- Legacy import is copy-only and idempotent.
- Public configuration contains no secrets or local operator overrides.

### 18.2 Live gates

The local `operator_managed` profile preauthorizes bounded live conformance and
does not require per-call confirmation. Live gates still use exact finite tasks,
no automatic retry, accounting, and explicit result inspection:

- one complete multi-turn Grok Direct conversation;
- one complete multi-turn Qwythos Direct conversation;
- non-streaming atomic display;
- D-drive restart/reload;
- exact provider/model provenance;
- actual or explicitly unknown accounting;
- no hidden prompt.

GLM fan-out and a three-worker live batch are not v0.5 Direct Chat gates.

## 19. Delivery checkpoints

### Checkpoint A — shared core

Implement observation preservation, Candidate Vault, SQLite accounting,
dispatch leases and attribution, the return-contract compiler/validator,
contradiction preflight, census helper, and legacy compatibility. Publish an
exact commit and changed observable contract for independent offline replay.

### Checkpoint B — Direct runtime

Implement direct contracts, conversation/settings stores, provider-direct
adapters, full multi-turn context, and provider-specific dataset rules.

### Checkpoint C — local UI

Implement the loopback web service, launcher, non-streaming projection,
settings, history, health, and accounting surfaces.

### Checkpoint D — acceptance

Run all offline, multi-process, migration, and privacy gates, then the two
bounded live Direct conversations. External reviewers replay exact checkpoints;
their reports are evidence and proposals, not hidden co-maintainer authority.

## 20. Open-source preparation

- Commit only guarded defaults and credential-free examples.
- Ignore local settings, credentials, conversations, candidate bytes, ledgers,
  approvals, bills, and launch descriptors.
- Keep storage policy configurable and platform-portable while preserving the
  local D-only override.
- Document provider terms, cost uncertainty, data-retention uncertainty, and
  the difference between local policy and provider policy.
- Do not publish, release, deploy, or create a marketplace entry without a
  separate explicit authorization.

## 21. Alternatives rejected

### Separate MACR-Direct repository

Rejected because it would duplicate provider, credential, cost, error, and
policy logic and create two drifting runtimes.

### `TaskContract(mode="direct")`

Rejected because direct conversations and delegated work have incompatible
prompt, authority, lifecycle, storage, and acceptance semantics.

### Streaming UI

Rejected by operator preference and because future projection research should
consume immutable completed responses rather than token animation.

### Embedded Direct content inside Codex

Rejected because the direct plane must not route prompt content through an
OpenAI or Anthropic model context. Hosts may only open the local UI.

### Immediate cross-plane handoff

Rejected from v0.5 because selection, whole-thread transfer, and summaries each
lose necessary context or expose too much. It belongs to Context Capsule.

## 22. Delivery process constraints

- Do not use Codex subagents for implementation.
- GLM-5.3-Flash may be used only through MACR for short, non-sensitive,
  candidate-only tasks after the worker profile's max-reasoning completion
  problem is corrected.
- GLM receives no write, patch, verification, merge, or acceptance authority.
- Architecture, integration, review, verification, and merge remain the primary
  implementer's responsibility.
- Current readable speaker identity remains `unresolved` until a task-local,
  host-observed binding is explicitly established. Model and provider are not
  resident identity.

## 23. Resolved decisions

- One unified MACR core with parallel Codex and Claude host adapters.
- Equal initial provider, budget, and approval rights for both hosts.
- One management budget view with provider subaccounts.
- Budget behavior is warn-only for the local operator profile.
- Grok 4.6 and Qwythos are the only Direct Chat v0.1 models.
- GLM remains a restricted routine worker.
- Direct UI is a loopback local web application started on demand.
- Conversations are provider/model pinned.
- System prompt is blank by default and always visible when present.
- Direct records are plaintext in v0.1.
- Grok records are archive-only; Qwythos records are evaluation-only.
- Neither Direct dataset is locally training eligible.
- Qwythos canonical weights are immutable.
- Responses are non-streaming and projected only when complete.
- Full multi-turn history is preserved without hidden compaction.
- Cross-plane handoff is deferred to Context Capsule.
- Public default is guarded; local override is operator-managed.
- Paid-call confirmation is disabled locally, but accounting is mandatory.
- Automatic retries remain disabled.
- Future accounting AI owns authoritative reconciliation.
- Provider completion, return-contract validity, raw capture, materialization,
  verification, and acceptance remain separate observable states.
