## 0. Decision

MACR v0.6 evolves the runtime from an explicit provider dispatcher into a deterministic compiler for temporary AI coordination organizations.

The primary decision object is not a model ID. It is a versioned `CoordinationPlan` that binds:

```text
task + policy + context capsules + topology + role slots
+ qualified model-route bindings + verifier graph + accounting policy
```

Every generated result remains a candidate. Model discovery, qualification, selection, execution, verification, materialization, acceptance, merge, and deployment remain separate state transitions.

## 2. Core invariants

### I-01 — MODEL != ROLE != EXECUTION_ROUTE != RESIDENT != HOST_SESSION

A model is a computational service claim. A role is a task-local authority and context contract. An execution route is a provider endpoint plus configuration. A resident is a separately governed identity. A host session is a host-observed runtime binding.

No Model Passport, role slot, provider profile, model self-label, color, or familiar name creates resident identity.

### I-02 — DIRECT_PLANE != COORDINATION_PLANE

Direct Chat may support native provider conversations. It creates no verification or acceptance claim and its history enters a Coordination Plan only through an explicit Context Capsule selection.

The Coordination Plane owns plan compilation, role authority, dispatch, candidate capture, verification evidence, and accounting.

### I-03 — DISCOVERY_PROVIDER != EXECUTION_PROVIDER

A source may discover a model without being authorized to execute it. Discovery credentials and execution credentials use different namespaces and capability records.

### I-04 — OBSERVATION != EVIDENCE != QUALIFICATION != ELIGIBILITY != ACCEPTANCE

External catalog data is an observation. A MACR probe plus verifier result is evidence. A signed, versioned decision may qualify one exact model-route profile for one role. Eligibility is recalculated for a particular task and policy. Acceptance remains task-local.

### I-05 — HARD POLICY IS NOT A WEIGHT

Privacy, data classification, authority, identity resolution, qualification freshness, verifier availability, route allowlisting, and budget policy mode are hard eligibility gates. Price, latency, and market signals cannot compensate for a failed hard gate.

### I-06 — PASSPORT IS A PROJECTION

`ModelPassport` is a reproducible current view. Append-only source snapshots, observations, evidence items, qualification decisions, invalidations, and revocations are authoritative.

### I-07 — ALIAS != CONCRETE SUBJECT

Qualification never binds to `latest`, an auto-router, or an unresolved family alias. If a hosted service cannot expose a concrete revision, the identity state is `claimed` or `unresolved`, not `resolved`.

### I-08 — FALLBACK IS A NEW PLAN REVISION

No provider adapter silently substitutes another model. Retry, fallback, or escalation creates a new dispatch record tied to a new `plan_revision`, reason, cost observation, and authority check.

### I-09 — SAME SNAPSHOTS -> SAME PLAN

Given identical task bytes, Context Capsule digests, operator policy, qualification snapshot, route snapshot, availability snapshot, planner version, and tie-break rules, planning must produce byte-identical canonical JSON and plan digest.

### I-10 — EXTERNAL TEXT IS UNTRUSTED DATA

Catalog descriptions, model cards, rankings, webpages, benchmark prose, and search output never become system instructions, role policy, or execution authority.

## 3. High-level architecture

```text
External sources
  -> Untrusted Observation Zone
  -> immutable DiscoverySnapshot
  -> normalized ModelObservation
  -> Evidence / Identity Kernel
  -> Passport Projection
  -> Probe Queue
  -> role-route Qualification Decisions

Task + OperatorPolicyProfile + ContextCapsules
  -> hard Eligibility Compiler
  -> Topology Registry
  -> deterministic Shadow Planner
  -> CoordinationPlan + digest + exclusion reasons
  -> Execution Route Resolver
  -> authority / lease / queue / provider
  -> Candidate Vault
  -> typed Verification Graph
  -> Evidence + Accounting Outbox
  -> explicit Acceptance
```

The Model Observatory is advisory. The Coordination Plane consumes only normalized, versioned records from the Evidence / Identity Kernel.

## 4. Evidence and identity kernel

### 4.1 Model subject

```yaml
ModelSubject:
  subject_id: sha256
  vendor: string
  vendor_model_id: string
  concrete_revision: string | null
  identity_status: resolved | claimed | unresolved
  first_seen_snapshot_id: sha256
```

`subject_id` is derived from canonical identity fields, not display names.

### 4.2 Execution route identity

```yaml
ExecutionRouteIdentity:
  route_id: sha256
  model_subject_id: sha256
  provider_id: string
  endpoint_identity: string
  provider_model_id: string
  parameter_profile_digest: sha256
  prompt_compiler_version: string
  data_policy_snapshot_id: sha256
```

The same nominal model through direct Z.ai and a future OpenRouter route is two qualification subjects at the route layer.

### 4.3 Qualification key

```text
QualificationKey = sha256(
  model_subject_id
  + route_id
  + role_definition_digest
  + context_class
  + verifier_suite_digest
  + probe_definition_digest
)
```

Changing any component makes prior qualification inapplicable until explicitly re-evaluated.

### 4.4 Evidence records

Each evidence record includes source snapshot, producer, verifier, exact subject, timestamps, artifact/candidate digests, test counts, observed costs, negative controls, and blind spots. Corrections append; they never rewrite prior evidence.

## 5. Context Capsule

Context packaging is a first-class security and reproducibility boundary.

```yaml
ContextCapsule:
  capsule_id: sha256
  schema_version: 1
  source_items:
    - source_id: string
      byte_sha256: sha256
      selected_ranges: []
  compiled_bytes_sha256: sha256
  compiler_version: string
  token_estimate: integer
  data_classification: public | internal_approved | local_only
  redaction_profile: string
  allowed_role_ids: []
  allowed_route_ids: []
  expires_at: timestamp | null
  parent_capsule_ids: []
```

Rules:

- capsule construction is deterministic for exact source bytes and compiler version;
- local paths, secrets, resident-private data, and unpublished theory are not inferred safe;
- a Direct Chat transcript is not implicitly imported;
- child roles receive only capsules explicitly bound to them;
- planners receive capsule metadata and digests, not unrestricted source trees;
- changed source bytes invalidate the capsule.

## 6. Operator policy profile

Open-source deployments require configurable controls instead of one hardcoded operator style.

```yaml
OperatorPolicyProfile:
  profile_id: owner-warn-only-v1
  budget_mode: observe | warn | enforce
  approval_mode: exact_member | exact_batch | policy_session
  model_watch_enabled: false
  discovery_only: true
  auto_probe_max_cost_usd_per_day: 0
  production_promotion: explicit
  fallback_mode: explicit_plan_revision
  max_parallelism: 1
  direct_context_import: manual
  accounting_required: true
```

The current owner profile uses `budget_mode: warn`: cost is estimated and recorded, warning thresholds do not silently become hard stop authority. Task/provider hard safety gates remain independent.

No scheduler or watch automation is created merely by defining this schema.

## 7. External Model Observatory

### 7.1 First source

OpenRouter is the first discovery source, not a required inference provider. Public web and API adapters implement one `ModelDiscoveryProvider` protocol.

### 7.2 Snapshot contract

```yaml
DiscoverySnapshot:
  snapshot_id: sha256
  source_id: openrouter_models
  observed_at: timestamp
  request_shape_sha256: sha256
  raw_bytes_sha256: sha256
  normalized_bytes_sha256: sha256
  parser_version: string
  transport_metadata:
    etag: string | null
    last_modified: string | null
```

Raw bytes are immutable and private to the observation store. Public events contain only bounded metadata and digests.

### 7.3 Route-specific privacy observations

Retention, training, ZDR, data collection, region, caching, and terms are provider-endpoint observations with timestamps and source snapshots. They are not permanent model properties.

Unknown or ambiguous privacy policy is treated conservatively and can make a route ineligible.

### 7.4 Watch behavior

The default is manual discovery. A future low-frequency watch loop requires a separate explicit automation decision. Automatic probes remain disabled when daily probe budget is zero.

## 8. Passport projection and qualification

### 8.1 Passport projection

The Passport projects:

- concrete and claimed identity;
- discovery sources and freshness;
- route-specific capability and privacy observations;
- market observations;
- probe evidence;
- known failure modes;
- role-route qualifications;
- invalidations and blind spots.

Deleting or editing a Passport projection never deletes evidence; it is rebuildable.

### 8.2 Qualification states

```text
DISCOVERED -> SCREENED -> PROBE_QUEUED -> PROBED
PROBED -> QUALIFIED | SHADOW_ONLY | REJECTED
QUALIFIED -> STALE | SUSPENDED | REVOKED
STALE -> REQUALIFIED | REVOKED
```

### 8.3 Freshness vector

Qualification becomes stale when any bound model identity, route, parameter profile, prompt compiler, role definition, Context Capsule class, verifier suite, probe definition, or critical provider policy observation changes.

### 8.4 Probe evidence

Probe suites remain role-specific:

```text
P0 exact output
P1 structured JSON
P2 pure function
P3 bounded module
P4 whole-file rewrite
P5 cross-file pair
P6 tool-call contract
P7 coordinator decomposition
P8 reviewer discrimination
P9 long-horizon iteration
```

Probe definitions contain hidden/held-out variants, mutation controls, exact verifier versions, cost ceilings, and contamination notes. Terminal success is recorded separately from verifier success.

Qualification uses conservative confidence bounds and minimum sample counts, not a raw success percentage from a tiny sample.

## 9. Deterministic coordination planner

### 9.1 Inputs

```yaml
PlanningInput:
  task_digest: sha256
  task_descriptor: object
  context_capsule_ids: []
  operator_policy_snapshot_id: sha256
  qualification_snapshot_id: sha256
  route_snapshot_id: sha256
  availability_snapshot_id: sha256
  pricing_snapshot_id: sha256
  topology_registry_digest: sha256
  planner_version: string
```

### 9.2 Hard eligibility

A binding is eligible only if identity is sufficiently resolved, the role-route QualificationKey is current, privacy permits the route, required capabilities and verifier exist, Context Capsules permit the role/route, authority is within the role, and budget policy can be evaluated.

Every excluded candidate receives a stable reason code.

### 9.3 Ranking

After hard gates, ranking is lexicographic:

1. maximize the lower confidence bound of task-fit verified utility;
2. minimize expected total cost: generation + verification + integration + expected retry + human work;
3. satisfy latency objective;
4. prefer fresher direct evidence;
5. apply a canonical subject/route ID tie-break.

Popularity, newness, and external benchmark signals may rank the probe queue but never production bindings.

### 9.4 Plan output

```yaml
CoordinationPlan:
  plan_id: uuid
  plan_revision: integer
  plan_digest: sha256
  planner_version: string
  topology_id: string
  roles: []
  bindings: []
  context_capsule_ids: []
  verifier_graph: object
  policy_snapshot_ids: []
  evidence_snapshot_ids: []
  eligible_candidates: []
  excluded_candidates: []
  budget_evaluation: object
  fallback_rules: []
  acceptance_authority: host_only
```

The digest covers canonical JSON excluding `plan_id` but including `plan_revision`, all snapshot IDs, tie-break rules, context hashes, verifier versions, and chosen route parameters.

### 9.5 Shadow-first

The first planner cannot dispatch. It produces a shadow plan beside the explicit v0.5 route. Promotion from shadow to execution requires replay evidence and a separate authority decision.

## 10. Direct and coordinated planes

### Direct Plane

- raw provider conversation;
- multi-turn context controlled by the operator;
- no automatic qualification, verification, materialization, or acceptance claim;
- no automatic export to Context Capsules;
- no resident identity inference.

### Coordination Plane

- deterministic plan compilation;
- explicit role and Context Capsule binding;
- task/provider authority gates;
- candidate vault and verifier graph;
- append-only evidence and accounting;
- explicit host acceptance.

Provider adapters may be shared, but contexts, authority, and state transitions are not.

## 11. Topology registry

### T0 — DIRECT_VERIFIED

One worker, one typed verifier graph, host acceptance. This is the first executable v0.6 topology.

### T1 — FANOUT_VERIFIED

Multiple independently dispatched workers produce candidates; a deterministic comparator/verifier evaluates them. T1 remains shadow-only until the durable queue, leases, accounting, and a bounded live concurrency replay show no silent evidence loss.

### T2 — SUPERVISOR_WORKER

A coordinator proposes task decomposition. The runtime, not the coordinator, issues child authority and dispatch. The coordinator never inherits Mother/host authority.

### T3 — CROSSFILE_PAIR_EXPERIMENTAL

Workers share an exact canonical contract but receive separate Context Capsules. Each target path has an explicit lease and ownership record. Same-target work is permitted only as named competing alternatives and never auto-materializes both.

Individual verification and integration verification are separate. T3 cannot become production-qualified in v0.6 without compile-together, cross-file vectors, mutation controls, exact diff scope, and collision tests.

The following remain schema-only: debate, multi-judge, recursive delegation, hierarchical swarm, autonomous long-running teams, and persistent child residents.

## 12. Verification and acceptance

Verifier graphs are typed acyclic graphs of deterministic primitives where possible:

```text
schema validation, parsing, compilation, exact equality, byte contract,
hash, unit vectors, mutation controls, scope diff, static analysis,
integration contract, cross-file invariants, and policy checks
```

Every node records input digests, tool/version identity, output digest, status, and bounded diagnostics. A model reviewer may generate review evidence but is not a deterministic verifier unless a separate mechanical contract validates its output.

No worker or coordinator receives acceptance, merge, release, deployment, or resident-governance authority.

## 13. Accounting and future bill interface

The v0.5 accounting outbox remains the foundation. v0.6 adds cost classes:

```text
discovery_cost
probe_cost
production_execution_cost
verification_cost
integration_cost
human_correction_observation
```

Each plan stores model subject, route, role, usage, observed price source, estimated/actual cost distinction, latency, candidate digest, verifier outcome, fallback reason, and acceptance state.

The future accounting AI integrates through an append-only bill/reconciliation port. v0.6 reserves stable identifiers for provider account, funding source, invoice item, plan, run, and accounting entry; it does not implement invoice ingestion.

## 14. Persistent state

Use a dedicated observatory/planning SQLite database rather than enlarging runtime operational payloads with external text.

Authoritative tables:

```text
model_subjects
execution_routes
source_snapshots
model_observations
evidence_items
qualification_decisions
qualification_invalidations
context_capsules
operator_policy_profiles
probe_definitions
probe_runs
topology_definitions
coordination_plans
plan_roles
plan_bindings
plan_events
```

`model_passports` is a rebuildable projection or SQL view, not authoritative evidence.

External descriptions and raw snapshot bodies never enter the runtime event/accounting databases. Cross-database changes use an outbox and visible reconciliation state; no code claims atomicity across independent databases.

## 16. Acceptance criteria

v0.6 is complete only when:

1. the baseline and migration evidence bind the exact accepted a4 state while preserving a3 ancestry;
2. model, role, route, resident, and host session remain distinct;
3. raw external data stays in the Untrusted Observation Zone;
4. OpenRouter discovery creates no inference authority;
5. identity aliases cannot receive qualification;
6. route-specific privacy and pricing observations are timestamped and versioned;
7. Passport projection rebuilds from append-only evidence;
8. qualifications bind the exact composite QualificationKey and become stale on bound changes;
9. Context Capsules are deterministic, scoped, and digest-bound;
10. operator budget/approval/watch policies are configurable and snapshotted;
11. hard safety gates run before ranking;
12. planner replay is byte-deterministic for fixed snapshots;
13. shadow planning produces explicit eligibility and exclusion reasons;
14. fallback creates a new plan revision and dispatch evidence;
15. T0 preserves candidate/verification/acceptance separation;
16. T1 has no duplicate dispatch, event loss, corrupt evidence, or unaccounted charge in synthetic and bounded live replay;
17. T2 coordinators cannot issue authority directly;
18. T3 uses target ownership/leases and compile-together integration gates;
19. current GLM evidence imports without upgrading unproven roles;
20. discovery, probe, execution, verification, and reconciliation costs remain separate;
21. Direct Plane history never enters coordination context implicitly;
22. no worker receives acceptance, merge, deployment, or resident authority;
23. exact external-source and code blind spots remain visible;
24. full offline verification and independent replay bind the release commit/tree.

## 17. Explicit non-goals

v0.6 does not implement persistent child residents, autonomous identity, unrestricted recursive delegation, autonomous acceptance, OpenRouter inference billing, universal provider API unification, automatic benchmark trust, automatic production promotion, unlimited swarm execution, automatic model-watch scheduling, invoice ingestion, or LLM-authored authority policy.
